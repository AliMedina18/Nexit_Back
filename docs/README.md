# Documentación de Nexit — índice por fase

Este índice existe para que cualquiera (incluida una futura sesión) pueda retomar el proyecto sin tener que adivinar en qué orden leer los documentos. Cada archivo lleva un número que refleja el orden en que se hicieron las cosas, no necesariamente el orden en que conviene leerlas si solo quieres entender "dónde estamos hoy" — para eso, empieza por el resumen de abajo y entra al documento que te interesa.

## Resumen de dónde estamos

1. Se analizó a fondo la operación real de Next (Excel históricos + prototipo HTML) y se diseñó el modelo de datos → **Fase 1, completa.**
2. Se diseñó y construyó el backend (Clean Architecture, .NET 8): las 4 capas, los controladores, autenticación JWT, autorización → **Fase 2 (construcción del backend), completa — ver los documentos 02 y 03.**
3. Se auditó ese backend (funcionalidad + seguridad) y se aplicaron las correcciones que no dependen de que exista todavía un proyecto de Supabase real → **hecho el 2026-08-17, ver el documento 04 y el 05.**
4. Se diseñó e implementó el modelo de permisos de 4 niveles (super_admin/admin/manager/miembro), con el flujo de solicitudes de eliminación para clientes/proveedores/proyectos → **hecho el 2026-08-18, ver el documento 06.**
5. Se construyó la lógica de backend del calendario de proyectos (por mes/año, eficiente), se restringieron los informes a solo super_admin/admin, y se agregó exportación a Excel de informes → **hecho el 2026-08-18, ver el documento 07.**
6. Se agregó la capa de pruebas funcionales (Postgres real con Testcontainers, encontró y corrigió un bug real de guardado) y una capa de pruebas de seguridad (autorización por defecto, límite de peticiones, inyección SQL, mass assignment, autorización a nivel de objeto), y se eliminó una dependencia vulnerable sin usar (AutoMapper) → **hecho el 2026-08-18, ver el documento 08.**
7. Se agregó la validación de dominio de correo también en la aplicación (no solo en el trigger de Postgres) al registrar un usuario, y se documentó paso a paso cómo crear el proyecto de Supabase (cuenta gratuita ahora, y cómo repetirlo con plan Pro y correo corporativo cuando esté listo), incluida la cuenta del primer super_admin y el registro de la segunda cuenta real (Yuliana Navarro, admin) → **hecho el 2026-08-20, ver el documento 09.**
8. Se documentó a detalle, para arrancar el frontend (que vive en otro repositorio), qué hace y qué no hace el backend con correos y autenticación: todo el envío real de correos (invitaciones, códigos de acceso) lo hace Supabase Auth directamente, no este backend; y qué falta (invitar+registrar en un solo paso, notificaciones de solicitudes de eliminación, recuperar contraseña) → **hecho el 2026-08-21, ver el documento 10.**
9. Se documentó, también para el frontend, el recorrido completo del sistema módulo por módulo (clientes, proveedores + adjuntos, proyectos + equipo + seguimiento, calendario, catálogos, informes, usuarios, solicitudes de eliminación): campos exactos, reglas de validación, permisos por rol en cada endpoint, y comportamientos transversales (reemplazo completo de colecciones hijas en cada PUT, sin paginación/búsqueda server-side, formato de errores) → **hecho el 2026-08-21, ver el documento 11.**
10. Se cambió el diseño de login: ya no es "solo la super administradora tiene contraseña" — ahora **todos los roles** entran la primera vez con código OTP y ahí mismo crean su contraseña, para usarla de ahí en adelante (más un flujo de cambiarla/recuperarla más tarde). Se actualizó el documento 10 con el diseño nuevo y se empezó el backlog de historias de usuario (login como HU-01/HU-02, y qué ve cada rol como HU-03) → **hecho el 2026-08-21, ver el documento 12.**
11. Se decidió crear el proyecto de Supabase directo en plan **Pro** (no gratis-y-migrar-después como decía el documento 09 originalmente), dimensionado para hasta 25 personas, y conectar un proveedor de correo transaccional (Resend recomendado) **antes** de crear el proyecto, para que los códigos OTP funcionen desde el día uno sin el límite de 2 correos/hora del servidor de pruebas de Supabase → **hecho el 2026-08-21, ver el documento 13** (reordena y ajusta los pasos del documento 09, no lo reemplaza por completo).
12. Se creó el proyecto real de Supabase (Pro), se conectó `Nexit_Back` en producción contra él (Session pooler, rol `nexit_app` de mínimo privilegio), se corrigió un bug real de orden de ejecución de los scripts SQL, y se resolvieron las 5 advertencias "Function Search Path Mutable" del Security Advisor → **hecho el 2026-08-23, ver los documentos 09 y 13, y `schema/05`.**
13. Se diseñaron y aplicaron las tres plantillas de correo de autenticación con la identidad de marca de Nexit (login por código, restablecer contraseña, y la notificación de seguridad de contraseña cambiada), y se definió la política de contraseñas (mínimo 10 caracteres, mayúscula, minúscula, número y símbolo) → **hecho el 2026-08-23, ver los documentos 14, 15 y 16, y la sección 7 del documento 10.**
14. Se completó el módulo de usuarios: desactivar ahora bloquea el acceso de verdad (no solo lo marcaba en la base), y se agregó la eliminación automática tras 30 días desactivado, con respaldo previo en `usuarios_eliminados` — siguiendo el mismo patrón de otros productos (Microsoft Entra ID, GitLab, Facebook) → **hecho el 2026-08-23, ver el documento 17 y `schema/06`.**
15. Se agregó la historia de cerrar sesión (HU-07, 100% Supabase, sin código nuevo) y, en `docs/17`, la recomendación concreta para acortar la ventana de token válido tras desactivar/cerrar sesión (bajar el JWT expiry en el dashboard de Supabase) → **hecho el 2026-08-23, ver el documento 12 (HU-07) y la sección 6 del documento 17.**
16. Se corrigió el cálculo de mes/año del calendario de proyectos: ahora se decide por la hora LOCAL de la sede de cada proyecto (Bogotá o México, según `SedeNext`), no por UTC ni por la zona horaria de sesión del servidor — evita que un proyecto tarde en la noche cerca de fin de mes aparezca en el mes siguiente → **hecho el 2026-08-23, ver el documento 18.**
17. Se construyeron las tres piezas que faltaban del flujo de solicitudes de eliminación y de proveedores: notificaciones en bandeja (con la regla de que una sola decisión del administrador resuelve todas las solicitudes pendientes de la misma entidad), historial de cambios por campo para proyectos/proveedores/clientes (tipo Google Docs/Excel), y el marcado propio "trabajando con este proveedor" (público, muchos-a-muchos, alimenta la vista "mis proveedores") → **hecho el 2026-08-24, ver el documento 20 (HU-08 en el documento 12) y `schema/07`.**
18. Se investigó cómo otros sistemas resuelven "a qué proveedor/cliente/proyecto atender primero" (lead scoring de CRM, RFM, tiering de proveedores, next-best-action con IA, microagentes que leen notas de texto libre) y se dejó una propuesta concreta de 3 niveles usando datos que Nexit ya captura (Nivel 1: rúbrica de puntos transparente, sin IA; Nivel 2: microagente de IA opcional que lee notas/bitácora; Nivel 3: aprendizaje de casos pasados, a futuro) → **hecho el 2026-08-24, ver el documento 21.**
19. La usuaria confirmó empezar por el Nivel 1 (reglas, sin IA todavía) — se construyó y probó para proyectos: `GET /api/proyectos/prioridad` devuelve los proyectos activos puntuados de 0 a 100 con la lista de razones de cada puntaje (evento cercano, prioridad manual, sin actividad reciente, propuesta/brief pendientes, sin pagar con el evento cerca) → **hecho el 2026-08-24, ver el documento 22 (HU-09 en el documento 12).**
20. Se revisaron a fondo los dos proyectos de referencia que la usuaria descargó (`retail-supply-chain-analytics-main` y OmniSupply, un multi-agente de IA de verdad): ningún código es reutilizable (Python, y OmniSupply además tiene licencia GPLv3 pese a que el README dice MIT), pero se rescataron dos ideas de diseño y una validación clave — incluso el sistema de IA calcula el puntaje de riesgo con aritmética 100% determinística por reglas, y solo usa el modelo de lenguaje para redactar el resumen, el mismo patrón que ya se eligió para Nexit → **hecho el 2026-08-24, ver el documento 23.**
21. La usuaria confirmó que no se va a usar IA (sin presupuesto para eso) pero sí quiere la misma lógica de esos dos proyectos, traducida a C#/.NET — se extendió la rúbrica de puntos de `docs/22` a proveedores (`GET /api/proveedores/prioridad`: Score bajo, sin calificar pero ya usado, buen proveedor sin uso reciente, colaboradores sin proyecto formal) y a clientes (`GET /api/clientes/prioridad`: recencia y frecuencia, tipo RFM) → **hecho el 2026-08-24, ver el documento 24 (HU-10 en el documento 12).**
22. Se construyó el único hueco real de backend que quedó al revisar "qué falta" (`docs/10`, sección 5): invitar y registrar a alguien del equipo en un solo paso desde dentro de Nexit, con la persona invitada aceptando o rechazando ella misma (con un mensaje de quien invita) la primera vez que entra → **hecho el 2026-08-24, ver el documento 25 (HU-11 en el documento 12).**
23. Se registraron dos cuentas nuevas de administrador pendientes de invitar (`administracion@agencianextmkt.com`, `andresacuna@agencianextmkt.com`, rol `admin`) y se documentó — sin construir todavía, quedan preguntas de diseño abiertas — la propuesta de presencia en vivo para administradores ("quién tiene el sistema abierto ahora mismo", tipo Microsoft Teams), pedida por WhatsApp → **hecho el 2026-08-25, ver el documento 26 (HU-12 en el documento 12).**
24. Se configuró `Supabase:ProjectUrl`/`Supabase:ServiceRoleKey` en `appsettings.Production.json` (contra el proyecto real), se activó el Auth Hook, y se encontró y corrigió un bug real de producción: Row Level Security bloqueaba la lectura del rol de cualquier persona dentro del propio Auth Hook (por un GRANT de tabla sin la política de RLS correspondiente para `supabase_auth_admin`), así que **nadie** — ni la super administradora real — habría podido pasar ninguna verificación de rol hasta corregirlo. Se confirmó SMTP de Gmail ya conectado. Se decidió posponer el envío de invitaciones reales hasta tener el backend desplegado → **hecho el 2026-08-25, ver el documento 27 y `schema/09_fix_rls_auth_hook.sql`.**
25. Pendiente: elegir dónde desplegar el backend (candidatos evaluados con costo real: Azure B1 ~US$13.14/mes ≈ $40,300 COP/mes para 20-25 personas, y candidatos gratuitos Azure App Service F1/Render free con sus limitaciones — ver la conversación de esta sesión), completar `ForwardedHeaders:KnownProxies`/`KnownNetworks` una vez elegido, definir el Site URL/Redirect URLs de Supabase cuando el frontend esté más avanzado, disparar las tres invitaciones pendientes (Yuliana, `administracion@`, `andresacuna@`) una vez haya sistema desplegado (con el texto del correo ya rediseñado para no prometer acceso inmediato), avanzar con el frontend siguiendo el backlog de historias de usuario del documento 12, con el detalle de cada módulo en el documento 11. También pendiente, sin backend todavía por faltar más definición (no es un factor externo): qué mejorar específicamente del informe semanal (ver documento 20), ajustar los pesos de las tres rúbricas de prioridad con casos reales (ver documentos 22 y 24), y las preguntas de diseño abiertas de la presencia en vivo (ver documento 26).
26. Se construyó la subida real de archivos adjuntos de proveedores (PDF/Excel) a Supabase Storage — bucket privado con límite de 20MB y validación de tipo en dos capas, endpoints de subir/descargar (URL firmada temporal), borrado en cascada del archivo al eliminar el adjunto, y la aclaración de que la base de datos nunca guarda los bytes del archivo (solo la referencia), por lo que el volumen de archivos no afecta su rendimiento. Migración aplicada a `nexit_dev` y compilación/pruebas confirmadas por la usuaria (234 pruebas, 8 nuevas, cero regresiones) → **hecho el 2026-08-25, ver el documento 28 (HU-13 en el documento 12).**
27. Se cerraron las tres últimas historias de usuario que dependían de pasos manuales en Supabase: **HU-06** (desactivación/eliminación automática) ya estaba resuelta — se verificó directamente contra el proyecto real que los scripts ya habían corrido, sin necesitar ninguna acción — y **HU-04/HU-05** (recuperar contraseña y aviso de contraseña cambiada) se cerraron con una prueba real de punta a punta: se disparó un `resetPasswordForEmail` real contra `analistacompras@agencianextmkt.com`, se verificó el código de recuperación, se confirmó que las dos plantillas de correo (ya pegadas por la usuaria) llegan bien formateadas, se confirmó la política de contraseña completa activa en el dashboard, y se completó un cambio de contraseña real que disparó el correo de aviso de seguridad — con esto, la contraseña real de esa cuenta quedó actualizada. Con esto, **todas las historias de usuario documentadas en el backend (HU-01 a HU-13) quedan en ✅**, salvo la presencia en vivo (HU-12), que sigue en 🔴 a la espera de decisiones de diseño. Lo único pendiente del sistema completo es el despliegue del backend y avanzar con el frontend (ver el punto 25) → **hecho el 2026-08-25.**
28. Se investigó cómo otros sistemas resuelven la presencia en vivo (heartbeat + umbral de desconexión, y la función nativa de Supabase Realtime Presence como alternativa) y se construyó HU-12 con un heartbeat propio en `Nexit_Back` — `POST /api/presencia/ping` (cualquier autenticado) y `GET /api/presencia` (solo admin/super_admin, directorio con quién está en línea según el último ping, umbral configurable de 2 minutos por defecto) — se prefirió esto sobre Supabase Realtime Presence para mantener la autorización por rol consistente con el resto del backend, sin la complejidad extra de RLS sobre `realtime.messages`. Código y 9 pruebas nuevas listas, pendiente compilar/probar y aplicar la migración a `nexit_dev` (mismo paso pendiente que en el punto 26) → **hecho el 2026-08-25, ver el documento 29 (HU-12 en el documento 12, `docs/26` queda como referencia histórica del pedido original).**
29. Al construir el punto 28 apareció un bug real de compilación (un caso de uso de `Nexit.Application` referenció por accidente un tipo de Entity Framework Core, algo que esa capa nunca debe hacer en Clean Architecture) — se corrigió, y además se usó ese bug real como motivo para investigar y agregar tipos de prueba que faltaban en el backend: **pruebas de arquitectura** (`NetArchTest.Rules`, nuevas, verifican solas que la separación entre Core/Application/Infrastructure/API se mantenga — habrían detectado ese bug automáticamente), **reporte de cobertura de código** navegable (`dotnet-reportgenerator-globaltool`, con un script listo `scripts/generar-reporte-cobertura.ps1`), y **pruebas de mutación** documentadas como chequeo manual opcional (`Stryker.NET`, no integradas a cada `dotnet test` por ser lentas). También se confirmó que la exportación a Excel de informes (`docs/07`) ya tenía pruebas reales desde antes (abren el `.xlsx` generado y verifican su contenido, no solo que se produjeron bytes). Todo documentado en `docs/08-tipos-de-pruebas.md` → **hecho el 2026-08-25.**
